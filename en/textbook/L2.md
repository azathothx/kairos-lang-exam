# Kairos Grade 2 Textbook — Writing Kairos

**Version**: v1 (2026-08-02 · conforms to language 1.0 〈tracked 2026-11-04〉 · spec_head: v1.1.0) — English mirror of the Japanese original. The aim of Grade 2 is to **write a schedule definition yourself
from a business requirement sentence** (the level above Grade 3 = reading). The [language specification](https://kairos-lang.org/en/spec/) is always canonical —
this book only shows the way to write, and never redefines the specification.

**How to read this book**: understanding at Grade 2 **is complete with the text and the end-of-chapter exercises**. The reference links are for confirming against the canonical source (look the specification up
as a dictionary — start from examples with the [reference](https://kairos-lang.org/en/reference/)). Every
"Run it and read" example in the text is **execution-verified** (`# eval:` is the evaluation range · the block right after it is the actual output). The "▶ Open in the Playground" link under each example lets you run and modify it in the browser as is (no installation · [kairos-lang.org/en/playground](https://kairos-lang.org/en/playground/)).
And one Grade 2 habit: **once you write it, always run it and check**. Whether a composition is right is decided not by its looks but by its **output** —
that is why the grading criterion of the exercises is "identical output (alternative answers accepted)".

To reproduce with the CLI: `npx kairos-lang list --from a --to b --tz Asia/Tokyo definition.kairos` (put the a and b of `# eval: a..b`. Always pass `--tz` — the CLI defaults to the machine's time zone, and with a different one the dates come out as the previous day with a time).

## Chapter 1 Decomposing the requirement sentence — "generate → window → select → transform"

There is one form for composition. Assign the words of the requirement sentence to four roles, then place them in pipe order.

> The 25th of every month. But if that day is a weekend or a holiday, move it up to the preceding business day.

- "every month" — **window**. Cut by month: `within(month)`
- "the 25th" — **select**. The 25th day in the window: `nth(25)`
- "but … move it up" — **transform**. Move an invalid day to a valid day: `roll(Preceding, on: bizDay)`
- The material always comes from a **generator**: `everyDay`

**Run it and read** — the assembled finished form. The holiday data and the business-day derivation go on the premise side:

```kairos
# eval: 2026-07-01..2026-11-01
premise JP {
  calendar-system: Gregorian
  tz: "Asia/Tokyo"
  wkst: Mon
}

@JP
holidays2026 = [2026-01-01, 2026-01-12, 2026-02-11, 2026-02-23, 2026-03-20,
                2026-04-29, 2026-05-03, 2026-05-04, 2026-05-05, 2026-05-06,
                2026-07-20, 2026-08-11, 2026-09-21, 2026-09-22, 2026-09-23,
                2026-10-12, 2026-11-03, 2026-11-23] covering: 2026..2026
satSun = everyDay |> filter(d => weekday(d) == Sat or weekday(d) == Sun)
bizDay = everyDay \ (satSun | holidays2026)

everyDay |> within(month) |> nth(25) |> roll(Preceding, on: bizDay)
```

```text
2026-07-24
2026-08-25
2026-09-25
2026-10-23
# 被覆サマリ
#   holidays2026 covering 2026-01-01..2026-12-31 残走路 61 日
```

## Chapter 2 "Nth" and "last" — selecting within the window

For requirements like "the second Friday" or "the last Friday", the form is to **narrow what to select first, then count within the window**.

```kairos
everyDay |> filter(d => weekday(d) == Fri) |> within(month) |> nth(2)
```

Build the sequence of Fridays only, then take the 2nd element of the month window. Reverse the order and it turns into "the 2nd of each month, when it is a Friday"
(this trap is in the exercises). "Last" can be written two ways — `within(month) |> last` (the last within the window) and
`monthEnd |> roll(Preceding, on: Friday sequence)` (move back from the end of the month). Same output; choose by
how you prefer to read it aloud. The `on:` of `roll` also accepts **an inline sequence with no name** (an anonymous axis).

**Run it and read** — the roll form of the last Friday:

```kairos
# eval: 2026-08-01..2026-12-01
premise JP {
  calendar-system: Gregorian
  tz: "Asia/Tokyo"
  wkst: Mon
}

@JP
monthEnd |> roll(Preceding, on: (everyDay |> filter(d => weekday(d) == Fri)))
```

```text
2026-08-28
2026-09-25
2026-10-30
2026-11-27
```

## Chapter 3 Business days and roll — the business decides the direction

`roll(Preceding)` moves back, `roll(Following)` moves forward. **Which way to fall is decided not by the grammar but by the business meaning** —
payroll (the paying side moves up) is Preceding, the due date of an invoice (the receiving side's deadline) is Following, as
commercial custom goes. Miss the one word "move up / move down" in the requirement sentence and the expression is clean but the business breaks.

**Run it and read** — the same "25th of every month" dropped in both directions. The premises are the same as in Chapter 1:

```kairos
# eval: 2026-07-01..2026-11-01
premise JP {
  calendar-system: Gregorian
  tz: "Asia/Tokyo"
  wkst: Mon
}

@JP
holidays2026 = [2026-01-01, 2026-01-12, 2026-02-11, 2026-02-23, 2026-03-20,
                2026-04-29, 2026-05-03, 2026-05-04, 2026-05-05, 2026-05-06,
                2026-07-20, 2026-08-11, 2026-09-21, 2026-09-22, 2026-09-23,
                2026-10-12, 2026-11-03, 2026-11-23] covering: 2026..2026
satSun = everyDay |> filter(d => weekday(d) == Sat or weekday(d) == Sun)
bizDay = everyDay \ (satSun | holidays2026)

everyDay |> within(month) |> nth(25) |> roll(Preceding, on: bizDay)   # 式 1: 給料日（前倒し）

everyDay |> within(month) |> nth(25) |> roll(Following, on: bizDay)   # 式 2: 支払期日（後ろ倒し）
```

```text
# 式 1（4 件）
2026-07-24
2026-08-25
2026-09-25
2026-10-23
# 式 2（4 件）
2026-07-27
2026-08-25
2026-09-25
2026-10-26
# 被覆サマリ
#   holidays2026 covering 2026-01-01..2026-12-31 残走路 61 日
```

## Chapter 4 Value-expression filter — writing conditions as formulas

Conditions that cannot be written by enumerating weekdays or ordinals are decided by **projecting the point's coordinates to values and testing with a formula**. For "gotōbi"
(五十日 — the 5th, 10th, 15th, 20th, 25th and 30th of every month), the remainder of `dayNo(d)` (the day number within the month) is
quicker than lining up six nth's:

**Run it and read**:

```kairos
# eval: 2026-09-01..2026-10-01
premise JP {
  calendar-system: Gregorian
  tz: "Asia/Tokyo"
  wkst: Mon
}

@JP
everyDay |> filter(d => dayNo(d) mod 5 == 0)
```

```text
2026-09-05
2026-09-10
2026-09-15
2026-09-20
2026-09-25
2026-09-30
```

[▶ Open in the Playground](https://kairos-lang.org/en/playground/#s=cHJlbWlzZSBKUCB7CiAgY2FsZW5kYXItc3lzdGVtOiBHcmVnb3JpYW4KICB0ejogIkFzaWEvVG9reW8iCiAgd2tzdDogTW9uCn0KCkBKUApldmVyeURheSB8PiBmaWx0ZXIoZCA9PiBkYXlObyhkKSBtb2QgNSA9PSAwKQ&f=2026-09-01&t=2026-10-01)

The 31st drops out naturally because `31 mod 5 == 1` — **turning the structure of the condition into an expression instead of an enumeration** is where the value-expression
filter is used. The available projections are `dayNo` / `monthNo` / `yearNo` · the weekday label `weekday(d)` and so on
(examples on each reference page).

- Read first: [reference/filter](https://kairos-lang.org/en/reference/filter.html) (with examples)
- To confirm against the canonical source: [spec §4.9 (window → value projection)](https://kairos-lang.org/en/spec/30-body-layer.html)

## Chapter 5 Composing rules with combinators

A requirement that cannot be written as a single pipe is **built as one sequence per rule and composed with combinators**. Since
`nth` takes only one ordinal, "the first and third Monday" is written as the **union** of two sequences:

**Run it and read** — naming the parts with bindings removes the duplication:

```kairos
# eval: 2026-09-01..2026-11-01
premise JP {
  calendar-system: Gregorian
  tz: "Asia/Tokyo"
  wkst: Mon
}

@JP
mondays = everyDay |> filter(d => weekday(d) == Mon)
(mondays |> within(month) |> nth(1)) | (mondays |> within(month) |> nth(3))
```

```text
2026-09-07
2026-09-21
2026-10-05
2026-10-19
```

[▶ Open in the Playground](https://kairos-lang.org/en/playground/#s=cHJlbWlzZSBKUCB7CiAgY2FsZW5kYXItc3lzdGVtOiBHcmVnb3JpYW4KICB0ejogIkFzaWEvVG9reW8iCiAgd2tzdDogTW9uCn0KCkBKUAptb25kYXlzID0gZXZlcnlEYXkgfD4gZmlsdGVyKGQgPT4gd2Vla2RheShkKSA9PSBNb24pCihtb25kYXlzIHw-IHdpdGhpbihtb250aCkgfD4gbnRoKDEpKSB8IChtb25kYXlzIHw-IHdpdGhpbihtb250aCkgfD4gbnRoKDMpKQ&f=2026-09-01&t=2026-11-01)

Union `|` is set union (the same point is normalized to one point) · intersection `&` is the points that appear in both · difference `\` is exclusion.
Two independent conditions like "Friday **and** the 13th" are an intersection; "business days **minus** closed days" is a difference —
**the conjunctions of the requirement sentence correspond to combinators**.

- Read first: [reference/combinators](https://kairos-lang.org/en/reference/combinators.html) (with examples)
- To confirm against the canonical source: [spec §4.5 (combinators)](https://kairos-lang.org/en/spec/30-body-layer.html)

## Closing — checklist for Grade 2

1. You can decompose a requirement sentence into "generate → window → select → transform" (Chapter 1)
2. You can write "Nth · last" in the order narrow → window (Chapter 2)
3. You can choose the direction of roll from the business meaning (Chapter 3)
4. You can turn a condition that cannot be enumerated into a value-expression filter (Chapter 4)
5. You can compose multiple rules with combinators (Chapter 5)

And **once you write it, run it**. The exercises at the end of each chapter accept "alternative answers if the output is identical" — composition practice goes all the way to comparing the output of your answer and the model answer
with the [reference implementation](https://github.com/azathothx/kairos-lang).
