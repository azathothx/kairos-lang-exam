# Kairos Grade 3 Textbook — Reading Kairos

**Version**: v1 (2026-08-02 · conforms to language 1.0 〈tracked 2026-11-04〉 · spec_head: v1.1.0) — English mirror of the Japanese original. The aim of Grade 3 is to **take a Kairos expression and read exactly
what fires**. The [language specification](https://kairos-lang.org/en/spec/) is always canonical — this book only shows
the way to read, and never redefines the specification. The exercises at the end of each chapter are the sample questions of this repository.

**How to read this book**: understanding at Grade 3 **is complete with the text and the end-of-chapter exercises**. The "Reference" at the end of each chapter is an entry point for when you want to confirm against the canonical source,
and is not required to read on — the specification is not a book to read from the start but a **dictionary** to
look things up in (start from examples with the [reference (descriptor reference)](https://kairos-lang.org/en/reference/),
and go to the spec when you want to confirm the normative wording). Every "Run it and read" example in the text is **execution-verified**:
the `# eval:` line is the evaluation range, the block right after it is the actual output of the reference implementation, and the verification runner of these materials
checks mechanically for drift from the specification. The "▶ Open in the Playground" link under each example lets you run and modify it in the browser as is (no installation · [kairos-lang.org/en/playground](https://kairos-lang.org/en/playground/)).

To reproduce with the CLI: `npx kairos-lang list --from a --to b --tz Asia/Tokyo definition.kairos` (put the a and b of `# eval: a..b`. Always pass `--tz` — the CLI defaults to the machine's time zone, and with a different one the dates come out as the previous day with a time).

## Chapter 1 The two layers — what is written where

Kairos source has two layers: the **premise layer** (premise 層 — supplying the premises) and the **body layer** (本体層 — the expression that
weaves the schedule).

**Run it and read** — these two layers run as is (`# eval:` is the evaluation range · below is the actual output):

```kairos
# eval: 2026-01-01..2026-04-01
premise JP {                 # ← ここから premise 層:
  calendar-system: Gregorian #    暦法・タイムゾーン・週の始まりなど
  tz: "Asia/Tokyo"           #    「式の解釈が成り立つ条件」を並べる
  wkst: Mon
}

@JP                          # ← 前提の束を指名して……
everyDay |> within(month) |> first   # ← ここが本体層: 供給された語彙で編む一行
```

```text
2026-01-01
2026-02-01
2026-03-01
```

## Chapter 2 Lexis and literals — the writable forms are fixed

- **Dates**: only the full form `YYYY-MM-DD`. **Only dates that exist can be written** — `2026-02-30` is a lexical error, and there is no
  rollover (reinterpreting it as March 2). The language guarantees "a written date exists".
- **Durations**: `1d` (civil day) · `2h30m` (elapsed time). Civil time and elapsed time cannot be mixed (`1d12h` is an error).
- **Standalone time**: `T09:00` (a wall-clock time with no date part. It becomes an instant only in the position where "a time is attached to a day",
  as in `everyDay |> at(T09:00)` — the argument of `at` is limited to this lexeme. ADR-51 · Supplement 13).
- **Strings**: `"Asia/Tokyo"` — used for tz and source values.
- **Range sugar**: `2026-01-30..2026-02-02` expands to 4 consecutive days in a table-element position.

A reading tip: when you see an unfamiliar sequence, check with the lexical rules of §5.5 whether "this is a date or a numeric expression".
For example, `2026-01` is not a date but a **numeric subtraction** (2026 − 1).

**Run it and read** — a nonexistent date is not silently corrected; it stops on the spot:

```kairos
# eval: 2026-01-01..2026-03-01
premise JP {
  calendar-system: Gregorian
  tz: "Asia/Tokyo"
  wkst: Mon
}

@JP
[2026-02-30]
```

```text
字句エラー(8:2): 実在しない日付: 2026-02-30（月は 01..12・日は月と閏年規則の実在日のみ——proleptic Gregorian 固定。F66/ADR-43）
```

## Chapter 3 Generators, windows, selectors — the backbone of an expression

The basic form of a body expression is the pipeline "**generate → cut by window → select**":

```kairos
everyDay |> within(month) |> first
```

- `everyDay` — the calendar-system-pure sequence of day ticks (generator · 生成子).
- `|> within(month)` — partitions by month windows (窓). Points are not discarded; they "belong" to a window.
- `|> first` — selects the first point **of each window**. A selector (選択子) is window-relative — not "the first point overall".

This gives "the 1st of every month". `last` gives the end of the month, `nth(25)` the 25th of each month. Note also that **the evaluation range is a half-open interval**
(`..2026-04-01` does not include April).

**Run it and read** — changing `first` to `last` alone gives the month-end sequence (the language also knows
that February has 28 days):

```kairos
# eval: 2026-01-01..2026-04-01
premise JP {
  calendar-system: Gregorian
  tz: "Asia/Tokyo"
  wkst: Mon
}

@JP
everyDay |> within(month) |> last
```

```text
2026-01-31
2026-02-28
2026-03-31
```

## Chapter 4 Premises change the meaning — how to read premise

A demonstration of the claim in Chapter 1. The next expression is "the first day of each week", but **which weekday fires is not written in the expression**:

```kairos
everyDay |> within(week) |> first
```

The answer is held by `wkst:` (the start of the week) in the premises — `wkst: Mon` gives a sequence of Mondays, `wkst: Sun`
a sequence of Sundays. Feeling you have answered after reading only the expression is the trap people fall into most at Grade 3, and the order **read the premise layer, then
read the body** becomes the form of reading. tz and calendar-system have the same structure (which calendar's "month",
which wall clock's "day").

**Run it and read** — the same single line evaluated under two premises. The weekday that comes out changes:

```kairos
# eval: 2026-01-05..2026-01-19
premise JPmon { calendar-system: Gregorian; tz: "Asia/Tokyo"; wkst: Mon }
premise JPsun { calendar-system: Gregorian; tz: "Asia/Tokyo"; wkst: Sun }

@JPmon
everyDay |> within(week) |> first   # 式 1: 月曜始まりの週の先頭

@JPsun
everyDay |> within(week) |> first   # 式 2: 同じ式・日曜始まり
```

```text
# 式 1（2 件）
2026-01-05
2026-01-12
# 式 2（2 件）
2026-01-11
2026-01-18
```

## Chapter 5 Combinators and filter — reading combinations

Multiple sequences are composed with combinators (結合子): `A | B` (union) · `A & B` (intersection) · `A \ B` (difference). The business-day idiom
`everyDay \ (satSun | holidays)` is read **from the inside out** as "from all days, subtract the union of weekends and holidays".

`filter` thins by a condition: `everyDay |> filter(d => weekday(d) == Fri)` is the sequence of Fridays only.
`weekday(d)` has the form "read the label of the window that point d belongs to" (binding-name projection), and at Grade 3 it is enough to
read it as "the weekday of d".

Remember also that **the order of the pipe decides the meaning** — `filter |> within |> nth(2)` (filter to Fridays,
then the 2nd in each month = the second Friday) and `within |> nth(2) |> filter` (the 2nd of each month, only when it is a Friday) are
different things. A real example of this trap is handled at Grade 2.

**Run it and read** — the business-day idiom. 2026-08-11 (Tue) is Mountain Day:

```kairos
# eval: 2026-08-10..2026-08-17
premise JP {
  calendar-system: Gregorian
  tz: "Asia/Tokyo"
  wkst: Mon
}

@JP
holidays = [2026-08-11] covering: 2026-08-01..2026-09-01
satSun = everyDay |> filter(d => weekday(d) == Sat or weekday(d) == Sun)
everyDay \ (satSun | holidays)
```

```text
2026-08-10
2026-08-12
2026-08-13
2026-08-14
# 被覆サマリ
#   holidays covering 2026-08-01..2026-09-01 残走路 16 日
```

## Closing — checklist for Grade 3

1. You can explain to someone the roles of the premise layer and the body layer (Chapter 1)
2. You can tell legal date and duration literals from lexical errors (Chapter 2)
3. You can read the "generate → window → select" pipe out loud (Chapter 3)
4. You have the habit of reading the premises before reading the expression (Chapter 4)
5. You can decompose a composition of combinators and filter from the inside out (Chapter 5)

If you can solve the 6 sample questions (at the end of each chapter) on your own, you are close to the Grade 3 level. When you want to confirm in a runtime,
run the "Verification" section at the end of each question with the [reference implementation](https://github.com/azathothx/kairos-lang).
